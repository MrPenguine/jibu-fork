# Local development

Two ways to run Jibu AI locally: **fully containerized** (recommended — one command, everything isolated) or **bare-process** (the original `start.sh`/pm2 flow, still fully supported for anyone who prefers it).

## 1. Install a container runtime

**[OrbStack](https://orbstack.dev/)** is the recommended runtime on macOS, especially Apple Silicon — it's lighter and faster than Docker Desktop, and is a drop-in replacement (same `docker`/`docker compose` CLI, same socket). **[Docker Desktop](https://www.docker.com/products/docker-desktop/)** is the documented fallback if you need its GUI or hit an OrbStack-specific edge case. **[Colima](https://github.com/abiosoft/colima)** is a free, scriptable alternative if you'd rather not run either app. All three are interchangeable here — nothing in this repo's Compose setup is runtime-specific.

## 2. Configure environment files

Each app has its own `.env`, copied from a committed `.env.example`:

```bash
cp .env.example .env
cp apps/backend/.env.example apps/backend/.env
cp apps/frontend/.env.example apps/frontend/.env
cp apps/worker/.env.example apps/worker/.env
cp apps/livekit-agent/.env.example apps/livekit-agent/.env
```

The root `.env` only covers infra container credentials (Postgres/Grafana/Vault) and has working defaults out of the box — you don't need to touch it for local dev.

### Secrets you must obtain yourself

| Variable | Where to get it |
|---|---|
| `GOOGLE_API_KEY` / `GEMINI_API_KEY` / `XAI_API_KEY` / `MISTRAL_API_KEY` / `OPENROUTER_API_KEY` | Whichever LLM provider(s) your agents use |
| `DEEPGRAM_API_KEY`, `ELEVENLABS_API_KEY`, `AZURE_SPEECH_KEY` | Whichever STT/TTS provider(s) your agents use |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_S3_BUCKET_NAME` | Your S3 bucket, for file storage |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Google Cloud Console, only if you want Google sign-in |
| `SUPABASE_URL` / `SUPABASE_API_KEY` / `SUPABASE_JWT_SECRET` | Your Supabase project |

Nothing else is required to bring the stack up — agents that need a provider you haven't configured just won't work until you add it.

### Secrets that are auto-generated or already have local defaults

| Variable | Where it comes from |
|---|---|
| `BETTER_AUTH_SECRET` | Auto-generated by `start.sh`. Generate manually with `openssl rand -base64 32` if you're not using `start.sh`. |
| `ENCRYPTION_MASTER_KEY` | Auto-generated by `start.sh` (must be exactly 64 hex chars / 32 bytes). Generate manually with `openssl rand -hex 32`. |
| `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` / `LIVEKIT_URL` | Already set to the local OSS LiveKit server's dev keys (`jibuapikey`/`jibuapisecret`, `ws://localhost:7880`) in the committed `.env.example` files. Only change these to point at a real LiveKit Cloud project. |
| Postgres / Grafana / Vault credentials | Default to `postgres`/`postgres`, `admin`/`admin`, and a dev root token respectively — see root `.env.example`. |

## 3. Bring everything up

```bash
docker compose up -d
```

No service list needed — this brings up the full stack: Postgres, Redis, Qdrant, Vault, LiveKit, the backend, frontend, worker, the LiveKit voice agent, plus Prometheus/Grafana/node-exporter for observability.

Check status:

```bash
docker compose ps
```

Everything should report `healthy` (not just `running`) within a couple of minutes. `worker` and `livekit-agent` have no HTTP listener to healthcheck — check their logs instead (`docker compose logs -f worker`) for a clean startup with no connection errors.

## 4. Verify

- Backend: `curl http://localhost:4000/api/health` → `{"status":"ok"}`. Swagger docs at `http://localhost:4000/api/docs`.
- Frontend: open `http://localhost:3000` — should load the login page.
- LiveKit agent: `docker compose logs -f livekit-agent` — look for it registering as a worker against the local LiveKit server.
- Observability: Prometheus targets at `http://localhost:9090/targets` should all show healthy; Grafana at `http://localhost:3100` (login `admin`/`admin` unless you changed it).

## Alternative: bare-process mode (no app containers)

The original flow still works exactly as before:

```bash
./start.sh          # foreground dev mode (nx serve + the Python agent directly)
./start.sh --daemon # pm2-managed background mode
./start.sh --stop   # stop everything
```

This brings up only the infra containers (Postgres, Redis, Qdrant, Vault, LiveKit, Prometheus, Grafana, node-exporter, n8n, Ollama) and runs the backend/frontend/worker/voice-agent as plain OS processes. Use this if you want hot-reload without rebuilding a container image on every change, or if you're debugging with a local debugger attached to a bare Node/Python process.

Don't run both modes' app processes at the same time — `docker compose up -d` (full stack) and `./start.sh` both try to bind the same ports (4000, 3000).

## Troubleshooting

- **A container reports `unhealthy`**: check its logs first (`docker compose logs -f <service>`). For `backend`, confirm `apps/backend/.env` has real values for anything the specific feature you're testing needs.
- **Frontend can't reach the backend**: confirm `BACKEND_URL` resolves in-network (`http://backend:4000`, set automatically in `docker-compose.yml` — not something you need to edit) rather than `localhost`.
- **LiveKit token/auth failures**: confirm `LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET` match between `apps/backend/.env`, `apps/livekit-agent/.env`, and `infra/livekit.yaml` (`jibuapikey`/`jibuapisecret` by default — don't change one without the others).
- **Vault/encryption errors on backend startup**: `ENCRYPTION_MASTER_KEY` must be exactly 64 hex characters. `openssl rand -hex 32` produces exactly that.
